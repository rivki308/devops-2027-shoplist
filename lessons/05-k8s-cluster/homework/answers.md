

\# חלק א׳ – רכיבי Kubernetes



| רכיב | איפה רץ? | מה התפקיד שלו? | אנלוגיה |

|---|---|---|---|

| API Server | ב-Control Plane (ההנהלה) | מקבל ומטפל בבקשות ל-Kubernetes | דלפק קבלת בקשות |

| etcd | ב-Control Plane (ההנהלה) | שומר את המידע על מצב הקלאסטר | ארכיון |

| Scheduler | ב-Control Plane (ההנהלה) | מחליט באיזה Node ירוץ כל Pod חדש | אחראי שיבוץ |

| Controller Manager | ב-Control Plane (ההנהלה) | דואג שהמצב בפועל יתאים למצב הרצוי | מפקח |

| Kubelet | בכל Node | מוודא שה-Pods שהוקצו ל-Node פועלים | אחראי משמרת בכל אתר |

| Container Runtime | בכל Node | אחראי להריץ את הקונטיינרים | מנוע |

| Kube-proxy | בכל Node | מסייע בניתוב תעבורת רשת ל-Pods | מכוון תנועה |

| CoreDNS | כ-Pods בתוך הקלאסטר | מאפשר למצוא Services לפי השם שלהם | ספר טלפונים |









\### תרחיש 1 – הגדלת מספר Pods



כאשר מריצים את הפקודה, Kubernetes מקבל בקשה להגדיל את מספר ה-Pods מ-2 ל-4. ה-API Server מקבל את הבקשה, וה-Deployment מתעדכן למספר הרצוי. ה-ReplicaSet דואג ליצור עוד שני Pods, ה-Scheduler משבץ אותם ב-Nodes, וה-Kubelet יחד עם Container Runtime מפעילים אותם.





\### תרחיש 2 – קריסת Backend



אם הקונטיינר של ה-Backend קורס, ה-Kubelet מזהה את התקלה ומנסה להפעיל אותו מחדש בהתאם למדיניות ההפעלה מחדש. אם ה-Pod כולו נמחק, ה-ReplicaSet שמנוהל על ידי ה-Deployment מזהה שחסר Pod ויוצר Pod חדש כדי לשמור על מספר ה-Pods שהוגדר.







\### תרחיש 3 – כיבוי Node



כאשר Node מספר 2 נכבה, Kubernetes מזהה שהוא אינו זמין. ה-Deployment וה-ReplicaSet דואגים ליצור Pods חלופיים, וה-Scheduler משבץ אותם ב-Nodes האחרים אם יש בהם מספיק משאבים. לעומת זאת, ב-Docker Desktop עם Node יחיד, אם המחשב נכבה, כל הקלאסטר אינו זמין ואין Node אחר שיכול להפעיל את ה-Pods.







\### תרחיש 4 – העברת ShopList ל-EKS



העברת הפרויקט לענן עלולה לגרום לשתי בעיות. ראשית, התמונה המקומית אינה קיימת אוטומטית ב-EKS, ולכן צריך להעלות אותה ל-Container Registry כמו Amazon ECR ולשנות את הגדרת המשיכה. שנית, NodePort אינו הדרך המקובלת לחשוף אפליקציה באינטרנט, ובדרך כלל משתמשים ב-LoadBalancer או ב-Ingress.









\### תרחיש 5 – Pod עצמאי לעומת Deployment



כאשר מוחקים Pod עצמאי שנוצר באמצעות kubectl run, הוא לא נוצר מחדש באופן אוטומטי. לעומת זאת, כאשר מוחקים Pod שמנוהל על ידי Deployment, ה-ReplicaSet מזהה שחסר Pod ויוצר אחד חדש. לכן, כדי ששירות Stats תמיד יחזור לפעול, יש להפעיל אותו באמצעות Deployment.
